# GoShare · 内网桌面共享

**单文件、免安装、无服务器**的局域网桌面共享工具：一台电脑点「我要分享」，同事点「我要观看」即可看到画面。
专为公司内网 / 会议室投屏 / 结对排查设计。

- 📦 **单 exe 分发**（约 17.8 MB），免安装、免管理员权限、无运行时依赖
- 🔒 **无服务器**：两台电脑 WebRTC 局域网直连（DTLS 加密），画面不出内网，也没有中继
- ⚡ **低延迟**：DXGI 桌面采集 + MJPEG 增量编码，实测端到端 **12~19 ms**（2K/30fps，环回）
- 🩹 **抗丢包**：分块级传输 + 三级画面修复，丢一块只影响它带的那几条带，不会黑屏
- 🇨🇳 全中文界面，双按钮入口，10 秒上手

> 平台：Windows 10 1809+（含 LTSC 2019）。技术栈：Go（`CGO_ENABLED=0`）· [Gio](https://gioui.org)（界面）· [pion/webrtc](https://github.com/pion/webrtc)（传输）· 标准库 `image/jpeg`（编码）。

## 快速开始

### 分享端（被看的一方）

1. 双击 `goshare.exe`，点 **「我要分享」**
2. 选择要分享的显示器（或点「框选区域」只分享屏幕的一部分），点 **「开始分享」**
3. 窗口自动最小化到托盘，界面上的 **IP 地址 + 授权码** 告诉同事即可
   （主窗最小化是刻意的：防止把自己的窗口采进画面形成"无限套娃"，见[技术原理](#dpi-与窗口处理)）
4. 屏幕顶部会出现一条**置顶悬浮条**（`正在分享 · N 人在看 · 停止`），可以拖到顺手的位置，下次自动复用
5. 想恢复窗口：双击托盘的蓝圆图标；想结束：托盘右键 →「停止分享」，或点悬浮条上的「停止」

### 观看端（看的一方）

1. 双击 `goshare.exe`，点 **「我要观看」**
2. 输入分享端的 **地址**（如 `192.168.1.5:9000`）和 **授权码**，点「接入」
   —— 同一内网也可以点「扫描」，自动发现正在分享的电脑
3. 画面右上角可切换 **「适配 / 1:1」**：适配 = 缩放看全屏；1:1 = 原始像素看细节（可拖动平移）
4. 底部状态栏实时显示 `fps · Mbps · 解码 ms · 延迟 ms`，断流/暂停会在画面上给出明确提示

### 分享中还能做什么

| 操作 | 说明 |
|---|---|
| 暂停分享 | 观众看到黑屏（1 fps 心跳，不会误以为断流）；再点恢复 |
| 更换区域 / 换屏 | 不中断分享，热切换到另一个区域或另一台显示器 |
| 轮换授权码 | 旧码立即失效，已接入的观众不受影响 |
| 踢出观众 | 观众列表里逐人踢出 |

## 技术原理

### 数据通路

```
分享端                                                            观看端
──────                                                            ──────
DXGI Desktop Duplication (BGRA, 物理像素, PerMonitorV2)
  │  桌面静止时不产帧 → 2s 心跳保活
  ├─ 自绘光标（不用采集库的 ShowsCursor，它会强制回退 GDI：4.8ms → 58.3ms）
  ▼
BGRA → I420 → 逐条带脏检测（bytes.Equal，走 SIMD）
  │  只编码"变化过的"横向条带；修复轮次/点名的条带也会被强制带上
  ▼
MJPEG 条带并行编码（每条带一个独立 JPEG，goroutine 池）
  ▼
GSJ2 分块：每块 = 完整帧头 + 若干**完整**条带（≤60KB，条带绝不跨块）
  ▼
pion/webrtc DataChannel ────────────────────────────────────────▶  SCTP 读 goroutine：只入队（单槽邮箱，满了覆盖最旧的）
  media: 无序 + 不重传（MaxRetransmits=0）                              │
  ctl:   可靠有序（PLI / 缺失位图 / Bye）                               ▼
  ICE 局域网 host 候选直连，DTLS 加密                            独立 goroutine：成批解析 + 并行解码（一批最多 4 块）
                                                                        │  条带写进持久画布（未出现的条带保留上一帧内容）
                                                                        ▼
                                                          画面缓冲池（复用内存，只同步变化过的条带行）
                                                                        ▼
                                                                  Gio 渲染（contain / 1:1）
```

信令走 HTTP（授权码校验、SDP 交换、观众管理），局域网发现走 UDP 广播。

### 为什么是 MJPEG，而不是 H.264 / VP9

| | MJPEG（本项目） | H.264 / VP9 |
|---|---|---|
| 帧间依赖 | **无**，每帧独立 | 有，丢一帧会污染后续帧 |
| 丢包表现 | 只丢那几条带，可精确补 | 花屏 / 需要关键帧才能恢复 |
| 新观众接入 | 天然秒开（下一帧即可解） | 必须等关键帧 |
| 分辨率热切换 | 直接切，解码器无需重配 | 需要重配解码器 |
| 纯 Go（无 CGO） | ✅ 标准库 | ❌ 需要 libx264/libvpx 或硬件 API |
| 码率 | **高**（这是唯一短板） | 低 3~10 倍 |

选型是实测出来的，不是拍脑袋：`go264` 的 Media Foundation 硬件编码在本机 `Encode()` **永久挂起**，
CPU 软编 1080p 只有 12.9 fps；而 MJPEG 条带并行下 2K 编码 **9.9 ms（101 fps）**、1080p **4.9 ms（206 fps）**。
码率短板用 **dirty tile 增量**补：静止桌面 5~10 Mbps，全量帧占比实测仅 **1.5~2.6%**。

### 线格式 GSJ2：一个消息 = 一个可独立解析的分块

```
0  .. 3   magic "GSJ2"          16 .. 17  width          25       refresh（修复轮次，0=稳态）
4  .. 11  seq (uint64)          18 .. 19  height         26       chunkIdx
12 .. 15  ts (uint32, ms 低位)  20 .. 21  totalTiles     27       chunkTotal
                                22 .. 23  tileH          28 .. 35 tilesMask（整帧的条带位图）
                                24        flags(bit0=全量帧)
36 ..     若干条带记录：index(uint16) · y0(uint16) · dataLen(uint32) · JPEG 数据
```

设计要点：

- **条带绝不跨块拆分**，每块自带完整帧头 → 收到一块就能解一块，**接收端没有任何重组状态机**。
  丢一块只丢它带的那几条带（实测：丢 1/9 块 → 17 条带里只缺 2 条）。
- `tilesMask` 让接收端**精确知道**该帧应该有哪些条带，于是"缺哪几条"是已知的，不是猜的。
- `refresh` 是修复轮次号，观众端据此判断"修复在飞，别重复请求"。
- 单个条带若超过 60KB（高细节画面），就**自己占一块更大的消息**——实测 pion↔pion 的 DataChannel
  512KB 消息照常送达，60KB 只是"保持丢失粒度细"的偏好，不是硬上限。
- ⚠️ 线格式变更会提升 `codec.ProtoVersion`，两端在 HTTP 接入阶段互报版本，
  不一致时直接返回 `409 双方版本不一致，请把两台机器都升级到同一版本`——
  而不是"接入成功但画面全黑"这种无法排查的静默失败。

### 三级画面修复

MJPEG 增量帧只覆盖"变化过的"条带，所以**丢失的条带不会自己回来**。修复分三级，代价从小到大：

1. **精确补发**（默认路径）：观众端把自己画布上"内容已过期"的条带位图通过 `ctl` 通道报上来
   （`CtlMissing`），分享端下一帧只补那几条。实测补 2 条带 = **1 帧 / 57 KB**（全量帧 460 KB 的 12%）。
2. **渐进式轮转修复**：不知道缺什么、或缺一大片时，分享端把"补齐整屏"分摊到约 10 帧，
   每帧多带 1/10 条带。实测从空画布 **9 帧铺满**，单帧最大 58 KB。
   这是替代"一发 2MB 全量帧突发"的关键——拥塞时那一发大概率整发丢掉，然后陷入"越要越堵、越堵越黑"。
3. **全量帧**：只在画布整体失效时用（分辨率变化 / 换屏 / 切档）。

请求侧还有两道闸：分享端对修复请求做 **800ms 冷却 + 在飞不重启**；观众端 **150ms 限流**上报缺失位图，
且 PLI 请求按 **300ms → 600ms → 1.2s → 2s 退避**，避免把修复流量变成新的拥塞源。

### 抗拥塞：延迟是"允许落后几帧"决定的

- **背压阈值按帧大小自适应**（约 1.5 帧，下限 512KB / 上限 4MB）。曾经是固定 8MB ≈ 4 个 2K 全量帧，
  等于允许落后 4 帧——光这一个数字就自带几百毫秒延迟。
- **latest-wins**：扇出侧发送前先看缓冲水位，超阈值就**整帧跳过**（不推进序号，下次拿最新的）；
  观众端邮箱同样只保留最新块。慢的一方丢帧，**绝不排队**。
- **解码不在 SCTP 读 goroutine 里**：读路径只做入队，解析+解码在独立 goroutine 上成批进行。
  否则读路径被自己的解码堵住，延迟单调增长，**连 ctl 通道（修复请求）一起被堵**。
- **批量解码**：单块通常只带 1~2 个条带，逐块串行解会把帧内并行度丢光（实测 2K 全量 7ms → 98ms）；
  成批解之后是 21.9ms，而端到端延迟反而从 47.5ms 降到 **18.0ms**（因为不用等整帧凑齐）。
- **自适应降档**：信号有两个——已发生的背压丢帧数，以及**缓冲水位**这个连续量（≥50% 即降档，
  首次降档不等冷却）。降档阶梯：JPEG 质量每档 −8（底线 42）→ 帧率 30 → 15；
  回升必须连续 10 秒干净（比降档慢，避免在临界点震荡）。

### 多观众扇出：编码一次，发送 N 次

每帧只 `encode + Marshal` 一次，结果放进原子共享缓存（`latest`）；每个观众有独立发送 goroutine，
被唤醒后读**最新**那份自己发。慢观众自然跳过中间帧，谁都不占采集/编码 goroutine 的时间。
（早期实现是每个观众各 Marshal 一次、全串在采集循环上，4 人时全员 fps 从 28+ 腰斩到 15。）

### DPI 与窗口处理

- 进程声明 **PerMonitorV2** DPI 感知，多屏混合缩放下坐标一律是物理像素
  （否则 `GetCursorPos` 返回逻辑像素，自绘光标会错位一个缩放倍数，而且错误完全自洽、极难发现）。
- **防自摄入**：分享开始后把主窗最小化——LTSC 17763 没有 `WDA_EXCLUDEFROMCAPTURE`，
  不最小化就会把自己的窗口采进画面，形成无限套娃（实测套 6~7 层），且每帧都在变、全量帧永不停止。
  认主窗用**标题精确匹配**（不是"第一个可见顶层窗"这种启发式：悬浮条也是本进程的顶层窗，
  曾经因此把悬浮条自己最小化了，而日志还报成功）。
- **悬浮条**是进程内第二个 Gio 窗口，靠 `SetWindowPos(HWND_TOPMOST)` 置顶。两个坑：
  置顶调用**返回成功不等于生效**（必须回读 `WS_EX_TOPMOST` 并重试）；
  Gio 的 `layout.Stack` 会把子项 Min 约束清零，导致 `Flex` 的 `SpaceBetween` 失效（要显式撑主轴 Min）。

## 实测性能

环境：Windows 10 LTSC 17763 · 2880×1800@175% 主屏 + 1920×1080@100% 副屏 · 20 逻辑核 · Intel Iris Xe ·
分享端与观看端同机（环回），所以数字是**下限**（真实无线环境会更差，CPU 也不与对方争抢）。

| 指标 | 1080p | 2K（2880×1800） |
|---|---|---|
| 采集（DXGI duplication） | ~1.2 ms | ~4.8 ms |
| 编码（全量帧） | 8~10 ms | 12~15 ms |
| 解码（成批） | 4~5 ms | 7~22 ms（全量/增量） |
| **端到端延迟**（编码完成→观众收到） | **13~14 ms** | **18 ms** |
| 画质 PSNR（源→经网络→解码） | 33.5~33.7 dB | 35.0 dB |
| 码率（活跃桌面，30fps） | ~32 Mbps | 33~52 Mbps |
| 码率（静止桌面） | 5~10 Mbps | 5~10 Mbps |

真机双进程实测（2K/30fps/1 观众）：**28~29 fps · 延迟 12~19 ms · 解码 3~5 ms · 画布完整 · 坏块 0**。

抗丢包（`netcheck` 的确定性用例，可复跑）：

| 场景 | 结果 |
|---|---|
| 丢掉 1/9 个分块（含 2 条带） | 画布 17 条带里 15 条仍有效，**只缺那 2 条** |
| 精确补发 | **1 帧补齐**，该帧 57 KB（全量帧 460 KB 的 12%） |
| 从空画布轮转修复 | **9 帧铺满**，单帧最大 58 KB，总流量 ≤ 一次全量帧 |

## 从源码构建

要求：**Go 1.26+**（`go.mod` 声明 1.26.4）、Windows 10 1809+、`CGO_ENABLED=0`（无需 C 工具链）。

```powershell
# 开发态（带控制台，便于看日志）
go build ./cmd/goshare

# 发布构建：单文件、无控制台、图标 + 版本信息 + PerMonitorV2 DPI manifest
powershell -File scripts/build.ps1 -Version 0.7.3
# 产出 dist/goshare-v0.7.3-windows-amd64.exe（约 17.8 MB）
```

`build.ps1` 会做四件事：生成图标 PNG → 用 `go-winres` 打包 Windows 资源（`.syso`）→ 编译 → 校验版本信息。
它已把 `GOPROXY` / `GOSUMDB` 设成国内可达的镜像。生成的 `rsrc_*.syso` 不入库，每次构建重新生成。

> ⚠️ 发布版的 `FileVersion` 来自 `winres/winres.json`，与 `-Version` 参数是两处；
> 改版本号时两边都要改，否则脚本会告警（文件名与 exe 内版本不一致）。

## 命令行参数

日常使用**不需要任何参数**。以下面向自动化与排障：

| 参数 | 说明 |
|---|---|
| `-port 9000` | 信令起始端口（被占用时自动顺延；**以日志里的实际端口为准**） |
| `-max 8` | 最多同时观看人数 |
| `-code 123456` | 固定授权码（默认每次随机） |
| `-display N` | 采集第 N 台显示器（默认主屏） |
| `-preset 最大` | 质量档位：`最大` / `流畅60` / `流畅30` / `急速` |
| `-log 文件` | 日志写到文件（发布版无控制台，排障时必加） |
| `-auto share\|watch` | 无人值守模式（配合 `-addr` / `-code-watch`，供自动化验证） |
| `-key-interval 30s` | 周期性开一轮渐进式修复的间隔（0 = 只靠观众请求恢复） |
| `-key-burst 3s` | 新观众接入后允许反复开修复轮次的窗口时长 |
| `-dump-frame 路径 -dump-at N` | 把观众端收到的第 N 帧落盘（回答"观众到底收到了什么"） |
| `-exit 30s` | 到时自动退出（自动化验证用；用独立定时器，不依赖渲染帧） |

## 防火墙说明（连不上时先看这里）

首次运行时 Windows 可能弹出「网络访问」确认框，**勾选「专用网络」并允许**即可。
如果被点了取消，或公司策略禁了弹窗，在分享端用**管理员终端**执行一次：

```bat
netsh advfirewall firewall add rule name="GoShare" dir=in action=allow protocol=TCP localport=9000
netsh advfirewall firewall add rule name="GoShare-UDP" dir=in action=allow protocol=UDP localport=50000-50100
netsh advfirewall firewall add rule name="GoShare-Discovery" dir=in action=allow protocol=UDP localport=45921
```

| 端口 | 协议 | 用途 |
|---|---|---|
| 9000（占用时自动顺延） | TCP | 信令：握手、授权码校验、版本握手、观众管理 |
| 50000–50100 | UDP | WebRTC 媒体：实际的画面数据 |
| 45921 | UDP | 局域网自动发现（广播）；禁用后仍可手动输地址接入 |

观看端**不需要**任何防火墙改动（出站连接默认放行）。

## 自检工具

这个仓库自带一套可复跑的验证工具（改完代码跑一遍，都是确定性判据）：

```powershell
go run ./cmd/capcheck     # 采集链路 12 项：后端选择/DPI/多屏/首帧黑帧预热/区域裁切
go run ./cmd/codeccheck   # 编解码 15 项：条带并行/增量不漂移/逐通道色彩保真/PSNR
go run ./cmd/sigcheck     # 信令 29 项：端口顺延/授权码/观众管理/多网卡地址排序
go run ./cmd/netcheck     # 端到端 21 项：真实 UDP+ICE+DTLS 跑通，含**丢块恢复**与延迟/PSNR
go run ./cmd/uicheck      # 界面 12 项：离屏渲染 + -golden 基线逐像素回归（锁屏也能跑）
go test ./...             # 自适应降档策略、背压阈值的确定性单测
```

两个值得单独说的门禁：

- `uicheck -golden testdata/ui-golden`：界面回归**必须**逐像素比对基线。粗统计（非黑占比/色数/亮部）
  抓不到"按钮整列消失"这类只改 2~4% 像素的缺陷。基线里还包含悬浮条的
  「停止按钮完整可见」与「二字垂直偏差 ≤1px」两条断言。
- `netcheck [4] 丢块恢复`：故意丢一个分块，断言"只缺它带的那几条带"，再断言精确补发/轮转修复
  的帧数与单帧体积——这是抗丢包能力的回归门禁，不靠肉眼。

> `capcheck` / `codeccheck` 里有几条**耗时阈值**类判据，机器忙时会抖动（连跑多个自检时尤其明显），
> 复跑即绿。真要判性能，先关掉别的负载。

`spike/` 下还有一批一次性的技术验证程序（编码器选型、DXGI 行为、置顶是否掐死帧事件等），
是上面那些结论的原始出处，保留可复现。

## 已知限制

- **仅 Windows**。非 Windows 平台有部分桩代码，但未适配、未测试。
- **纯局域网**：不含 STUN/TURN，不做 NAT 穿透，跨网段/公网连不上（这是设计取舍：画面不出内网）。
- **两端版本必须一致**：线格式版本不同会在接入时被明确拒绝（`409`），不会静默黑屏。
- **码率高于 H.264/VP9**：2K 活跃桌面 33~52 Mbps。无线环境下建议降到「流畅30」档，
  或只分享需要的区域（框选）。多人观看时出网码率是 `单路 × 人数`。
- **分享时主窗会最小化**：这是防自摄入的必要手段（目标平台 LTSC 17763 没有
  `WDA_EXCLUDEFROMCAPTURE`）。用托盘图标或悬浮条操作。
- 锁屏 / UAC 安全桌面下采集到的必然是黑屏（系统不给画面），此时悬浮条与界面会明确告警，
  不是程序故障。

## 常见问题

**观众连不上 / 卡在"连接中"**
九成是防火墙（见上节）。先确认分享端日志里的**实际端口**（被占用会顺延），手动输地址排除自动发现的问题。

**提示"双方版本不一致"**
两台机器的 exe 版本不同。线格式变过，必须两端都升级到同一版本。

**观众看到全黑**
分享端是不是锁屏了？锁屏时桌面停止产帧，属预期（界面会告警）。
否则让分享端点一下「暂停」再恢复，观众侧会自动请求修复。

**画面卡顿 / 模糊**
分享端把质量档位从「最大」降到「流畅 30」；观看端从「1:1」切回「适配」。
无线内网丢包高时画面会短暂缺几条带然后自动补齐（精确补发/轮转修复），有条件走有线。
状态栏的「延迟 ms」和日志里的「解码跳块 / 坏块 / 画布完整」是判断依据：
`解码跳块` 是观众端本机算力不足，`坏块` 才是链路/协议问题。

**画面看起来"卡住不动"**
先确认分享端的桌面**是否真的有变化**：桌面静止时 DXGI 不产帧，分享端会显示 `2.0 fps`（2 秒心跳），
这是预期行为，不是卡死。

**高分辨率副屏上光标位置不对**
不会。程序内嵌 PerMonitorV2 DPI 感知清单，多屏混合缩放下坐标均为物理像素。
若真遇到，请把 `goshare.exe -log goshare.log` 产生的日志发给维护者。
