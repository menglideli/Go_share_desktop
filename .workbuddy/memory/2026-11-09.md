# 2026-11-09 · P0-5 多端一致性（同步观看）落地

用户指定的最高优先项：**多台电脑在同一时刻显示同一帧**（一致性 > 延迟）。
按 `OPTIMIZATION.md` 的 P0-5 实施，D=80ms、严格同帧、不改线格式。

## 一、做了什么

1. **时钟同步**（`internal/rtc/peer.go` + `internal/rtc/clock.go`）
   - 新增 `CtlTimePing = 6` / `CtlTimePong = 7`，payload = 4×uint32 毫秒（16 字节）。
   - `rtc.Clock`：NTP 四时间戳公式 + **最小 RTT 过滤**（20 秒窗口），
     偏移/往返全部走 uint32 环绕 + int32 解释 —— 两端墙钟差几小时也没关系，
     只有差超过 24.8 天才失效。2 个样本才算同步，10 秒没有新样本自动失效。
   - 放在 `internal/rtc`（不是 `cmd/goshare`）是为了让 netcheck 跑**同一份**代码。

2. **统一呈现**（`cmd/goshare/playout.go`）
   - `due = 帧 TS + D - 偏移`，按 due 排序的小队列（深度 3），到点各上屏。
   - 迟到立即上屏；队列满丢新帧（保时间轴单调）；绝不排队。
   - `dispBufN` 3 → 5（队列 3 + 界面 1 + 余量 1）。

3. **落后可视化**（`CtlStats` + `signal.ViewerInfo.Token` + `ui.ViewerRow`）
   - 观众按**分享端时钟的 500ms 桶**采样，回报 `{seq, ts, lateMs, d, at}`；
     桶对齐是为了让分享端拿到的是"同一时刻"的帧号，可以直接比较。
   - 分享端每 3 秒打一条「同步检查」，观众列表显示 `#帧号 落后 N ms`，>200ms 标黄。

## 二、踩到的坑（最重要）

**单槽 latest-wins 调度器会活锁。** 第一版 playout 只保留最新一帧：
新帧的 due 总比上一帧晚一个帧间隔，一覆盖就把计时器往后推，
30fps + D=80ms 下**永远等不到到期**。表现极具迷惑性：

- 画面冻在某一帧（用户会以为"又卡了"）；
- 日志里"覆盖"（replaced）一直涨、"上屏"不涨；
- `晚 0ms` 一切正常，只有"显示 #N"不动。

改成按 due 排序的小队列后：28.8fps、队列丢弃 0、三个观众帧号完全相同。

**教训：任何"定时显示最新一帧"的设计，都要问一句"如果新帧到达速度 ≥ 定时器周期，
这个定时器还会触发吗"。** 阈值型设计（水位/队列深度）比"永远推后"的覆盖型安全。

## 三、"落后"不能用帧号算

发送侧背压丢帧会让帧号出现**永久空档**（实测 30 秒累计 7 个）。
拿 `hostFrames - viewerSeq` 当落后，会把"跳过 7 帧"错报成"落后 7 帧"，
而且在没有落后时也恒定非零（第一版实测显示"落后 16 帧"）。
正解：观众回报当前显示帧的 `TS`，分享端算 `(采样时刻 - TS) - D` —— 时间量纲，
不受序号空档影响。修完稳态恒为 0~1ms。

## 四、验收数字（本机 3 观众，2 个 D=80 + 1 个 D=0）

  `晚 0ms`、`落后 0ms`、队列丢弃 0；
- 观看端 28.8 fps · 延迟 3ms · 解码 ~1ms · 画布完整 54/55；
- D=0 观众不回报、不等待，行为与旧版一致（可回退）；
- netcheck 25/25（新增 `[5] 时钟同步` 4 项：偏移 +0ms、RTT 0ms、D=80 剩余 80ms、D=0 立即上屏）；
- uicheck 13/13（新增 `sharing-sync` 用例：正点 + 掉队标黄）；
- `go test ./...` 绿；capcheck 12/12、sigcheck 29/29。
