## 追加：跨设备分辨率适配（用户提出 2K 共享给 1K 屏看不清）

已实测并写入 PLAN.md 3.4，复现代码 `spike/scalebench`（`go run .`）。

**实测硬结论（i7-13700H 20 线程，CGO_ENABLED=0，源 2880×1800）**
- BGRA→I420：单线程 **26.14 ms**（超 30fps 预算）→ 并行 20 workers **4.29 ms**（6× 加速）
- RGBA 域缩放（x/image/draw）**完全不可用**：NearestNeighbor 63ms / ApproxBiLinear 110ms / BiLinear 174ms / CatmullRom 259ms
- I420 域缩放：box 2:1 单线程 4.88ms → 并行 **1.10ms**；bilinear 9.94ms → 并行 **2.05ms**
- 完整流水线并行：[A] 原生直发 2K **4.21ms** / [B] I420→box2:1 5.16ms / [C] BGRA box2:1→I420 **3.26ms** / [D] I420→bilinear 5.65ms

**架构决策**
- 必须并行化；**缩放只能在 I420 域做**（比 RGBA 域快 20~60×）
- 转换+缩放仅 4~6ms，编码才是大头 → **默认有能力直发原生分辨率**
- 降采样不可逆，优先"发原生 + 观看端缩放"，而非发送端预降
- 宽高比必须 contain（16:10→16:9 拉伸会变形），留黑边
- 四个子问题：宽高比、降采样糊文字、DPI 物理/逻辑像素混淆、降采样不可逆
- 观看端必备：1:1 原始尺寸 + 平移（看代码刚需）、区域放大 200%/400%
- 分辨率变更需重建编码器+发 IDR → 迟滞：变化 >20% 且持续 3s
- 多观看者不同需求 → 档位归并 ≤2 档，避免 N 个编码器

**新增阶段 0 spike**：S0-6 go264 编码 2K 耗时（<20ms/帧）、S0-7 观看端解码+GPU 缩放渲染清晰度

## 追加：观看端窗口模式与"切屏"（PLAN.md 3.5）

**修正了一个设计缺陷**：早期设想的"均衡档 = 观看端窗口 × 1.5 决定发送分辨率"是错的 —— 拖窗口是高频操作，会反复触发编码器重建（50~200ms + 重发 IDR），造成卡顿和 CPU 抖动。
**正确做法：发送分辨率与观看端窗口彻底解耦**，只由 主持人设定 + 网络带宽 + 编码耗时 决定；窗口变化仅影响本地 GPU 缩放（<1ms）。降档触发条件改为：丢包 >2% 或发送队列积压 >1s，且需连续 3s 才生效。

**窗口模式结论：默认窗口化 + 一键全屏，不默认全屏。**
- 理由：观看场景不单一（专心看 vs 边看边干），默认全屏太霸道
- 首次打开尺寸 = min(源 × 0.6, 屏幕工作区 × 0.8)，按源宽高比
- 三模式：适应窗口（默认）/ 1:1 原始尺寸可平移 / 全屏（F11、双击标题栏，仍按比例留黑边）
- 记忆窗口位置尺寸模式

**"切屏"两种含义都要支持**
- A. 观看端：多显示器拖动、指定显示器全屏、窗口置顶画中画
- B. 分享端切换共享屏幕/区域（更关键）：切换区域且输出分辨率不变 → 仅改裁切矩形，**编码器无需重建，无感**；切换显示器 → 重建采集+编码器 → 发新 SPS/PPS + IDR，约 0.5~1s
- 观看端必须能承受流中途分辨率变化：检测 SPS 变化 → 重建解码器（go264 能否原地重配置待验证）

**跨 DPI 拖动**：响应 `WM_DPICHANGED` 重算缩放，否则糊。

**新增 spike**：S0-8 流中途分辨率变化 / 解码器重建验证。
**新增风险**：R11（拖窗口触发重协商，已通过解耦消除）、R12（切屏导致解码器失效）、R13（跨 DPI 糊）

  `RateFactor > 0` / `QComp != 0` / `IPRatio != 0` / `PBRatio != 0` / `AQMode != Off` / `AQStrength != 0`
- 硬件路径实际只透传 `Width/Height/FPS/GOP/QP/BitrateKbps`
- **MF 后端未实现 `ForceKeyFrame`**（源码中仅 vaapi 实现）→ 印证原判断，秒开只能靠 GOP 缓存

## 🔴 决定性变更：编码器 H.264 → Motion JPEG

**go264 不可用（实测）**
- MF 硬编：`NewEncoder` 能拿到 `backend=mediafoundation`（392ms），但 **`Encode()` 永久挂起**（>15s）。
  `runtime.LockOSThread()`、`CoInitializeEx(MTA)` 两种绕过均无效 → 死锁，不可用
- CPU 软编（20 slices）：1080p **77.6ms/帧(12.9fps)**、2K **157ms(6.4fps)**、720p 56ms(17.9fps) → 全不达标

**Motion JPEG（标准库 `image/jpeg` + 水平条带并行）实测**

| 分辨率 | 编码(20条带) | 解码(20条带) | 帧大小 q75 | Mbps@30 |
|---|---|---|---|---|
| 2880×1800 | **9.9ms / 101fps** | 4.8ms / 210fps | 1.71MB | 410 |
| 1920×1080 | **4.9ms / 206fps** | 2.8ms / 364fps | 680KB | 165 |

标准库 jpeg 单线程 91.9ms@2K → 20 条带并行 9.9ms（**提速 ~8 倍**），这是方案可行的关键。

**判断依据**：内网千兆下**带宽不是瓶颈，延迟和 CPU 才是**。
**连锁简化**：每帧独立 → 天然秒开（GOP 缓存整个不需要）、丢帧不花屏、分辨率随意切、零外部依赖（去掉 go264 这颗雷）。

**代价与对策**：带宽 410Mbps@2K → 必须做 **dirty tile 增量更新**（只编码变化条带，屏幕多数时候只有小区域在动），H.264 做不到这么细。

## ⚠️ 踩过的坑（下次别再犯）

1. **喂同一帧测编码 → 大量 skip → 得出 28ms 的乐观假数据**（真实为 77.6ms）。性能测量必须用变化的帧
2. **`MotionSearchZero` 等"极速"配置反而更慢**（64→175ms）：运动补偿失效 → 全 intra 编码，帧从 3KB 暴涨到 1MB
3. **Gio 第一帧 `IsWindowVisible=0`**（ShowWindow 未完成），持续渲染到第 10 帧才是 1 —— 差点误判窗口没出来
4. **`GOSUMDB=off` 会让 screencapture 的 toolchain(go1.26.8) 校验失败**（该模块要求 go>=1.26.4，本机 1.26.3）→ 用 `GOSUMDB=sum.golang.google.cn`
5. PowerShell `Start-Process` 在本环境报"字典关键字 Path/PATH"冲突，且重定向输出为 UTF-16 → 用 `Out-File -Encoding utf8`
6. 后台跑 CPU 基准时不要用管道缓冲（`| Out-String`），否则看不到进度、卡死了也不知道卡在哪
