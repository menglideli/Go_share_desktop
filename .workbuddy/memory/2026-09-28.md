# 2026-09-28 · 悬浮条看不见/不刷新 + 卡顿延迟与黑屏（阶段 1+2）

用户报的四个问题：传输还能不能更快、悬浮窗显示不正常、卡时延迟很长、"同源传输和跳转"（澄清 =
观看端只追最新帧、不排队）、卡顿黑屏。

计划批准时选了**只做阶段 1+2**（不动线格式、不碰编码器），阶段 3（渐进式修复治黑屏）留到下一轮。

## 一、根因（都有真机证据，不是推测）

### 1. 悬浮条"显示不正常"= 被最小化停靠到屏幕外（一个 bug 三个症状）

`ownMainWindow`（internal/ui/winmin_windows.go）按"本进程第一个可见、无 owner 的顶层窗口"认主窗。
悬浮条在 `startShare` 里**先于**最小化被创建，新窗口位于 Z 序顶端 → `SW_MINIMIZE` 打到悬浮条身上。

真机窗口枚举（探针修正 DPI 虚拟化后）：

| 窗口 | IsIconic | 位置 | 结论 |
|---|---|---|---|
| 主窗 `GoShare · 内网桌面共享` | **0（没最小化）** | 正常 | 防自摄入其实失效了 |
| `goshare-hud` | **1（被最小化）** | (-32000,-32000) 停靠位 | 用户什么都看不到 |

而日志照样打「防自摄入：主窗已最小化」—— 在**错误的窗口上成功**，所以完全静默。三个症状一个根因：
①悬浮条看不见（位置/大小都不对）；②最小化的 Gio 窗口不再产生 FrameEvent（R22）→ 内容不刷新；
③防自摄入失效 → 主窗被自己采集（套娃回归），实测全量帧占比 **31%**。

第二轮还发现：Gio 建窗用 `CW_USEDEFAULT`，**Configure 之前**存在一个 339×56 的空标题瞬态窗，
它比主窗出现得早 —— "面积最大"这条兜底规则照样会挑错。最终改为**按标题精确匹配**
（`RegisterMainWindowTitle`）+ 面积下限（对最小化窗口豁免，因为最小化时 `GetWindowRect`
返回的是图标位小矩形 276×45，会把真主窗判成不合格 —— 实测把 `RestoreMainWindow` 弄挂过）。

### 2. 悬浮条布局：按钮不靠右

`Stack` 会把子项的 Min 约束清零，而 `Flex` 的 `SpaceBetween` 用的是 `mainMin - 内容宽`
→ 恒为 0 → 富余空间分配形同失效。表现：「停止」按钮紧跟文字，条体右侧空 85dp。
离屏基线（340×56）与真机截图**像素级一致地**这么画 —— 基线把 bug 一起固化了。
修法：进 Flex 前 `gtx.Constraints.Min = gtx.Constraints.Max`。
顺带把基线改成真实 dp 尺寸（320×46，175% 下 560×80）并新增 175% 用例。

### 3. 卡时延迟长：解码堵住了 SCTP 读 goroutine

`OnFrame` 跑在 pion 的 `OnMessage`（SCTP 读 goroutine）上，里面串了 `Decode`（2K 10~20ms）
+ `pixStat`（5.2M 像素抽样）+ `copyNRGBA`（2880×1800 一次 20MB 拷贝）+ `PushFrame`。
解码跟不上就排队 → 延迟单调增长，**连 ctl 通道（PLI）一起被堵**。
另外背压阈值固定 8MB ≈ 4 个 2K 全量帧，"允许落后 4 帧"本身就是几百毫秒；自适应控制器只认
"已经发生的丢帧数"（1s tick + 2s 冷却），所以"限速很慢"。

## 四、坑（已写进 PLAN.md R33~R38）

- **R33** 认主窗不能用启发式；"在错误的窗口上成功"是最贵的失败形态（必须留痕）。
- **R34** 置顶类调用**返回值 ≠ 状态生效**：实测 `SetWindowPos` 返回成功但 `WS_EX_TOPMOST` 是 0，
  要第 2~3 次才置上；判据必须回读实际状态并重试。外进程同参数却一次就成（差异未查明）。
- **R35** 解码绝不能放在 `OnMessage` 里；跳帧必须配"画布可能不完整"的上报。
- **R36** 背压阈值 = 允许落后几帧 = 卡顿时延迟上限。
- **R37** Gio `Stack` 清零子项 Min → `Flex.SpaceBetween` 失效。
- **R38** 探针不声明 DPI 感知会被 Windows 虚拟化坐标（本轮据此**误判**过一次"界面偏小 1.75 倍"，
  真值是 `PxPerDp=1.750`，Gio 的 DPI 处理本来就是对的）。

## 五、遗留（下一轮）

- **阶段 3（卡顿黑屏）未做**：增量帧天生不会自我修复，唯一手段是 PLI 要一整帧全量（2MB 突发），
  拥塞时又丢 → "越要越堵"正反馈。计划里的做法：条带轮转的**渐进式修复**（~10 帧铺满，单帧小、
  抗拥塞），wire 头用保留字节带 `RefreshID`（双向可退化），观众端按覆盖位图判定完整 + PLI 退避。
- **多观众扇出没压测**：本轮只跑了 1 个观众；4 人以上的极差需要另跑 `spike/multiview` 对照。
- **无线环境没实测**：调优结论建立在环回与有线，Wi-Fi 丢包下的表现要在用户的真实环境用
  「延迟 ms」这个新指标复测。
- `codeccheck` 的「2K 全量」是**既有**边界抖动（改动前的旧二进制同样 14/1：编码 20.5ms+解码 13.4ms
  卡在 30fps 门槛），与本次改动无关。
- `testdata/ui-golden/ui-hud.png` **此前从未入库**（只在开发机磁盘上），新基线 `ui-hud-175.png`
  也待入库 —— 否则别人 clone 后 uicheck 会报"基线缺失"。---

# 2026-09-28（第二轮）· 分块级传输 + 渐进式修复 + 观看端减负

用户提了三件事要我一起做（此前已议定方向）：
1. **分块级重组** —— 丢一块不再废整帧；
2. **渐进式修复** —— 替代"一发 2MB 全量突发"；
3. **削观看端单帧开销** —— pixStat 降频 + 去掉每帧 20MB 的 copyNRGBA。

## 结果（都有确定性证据）

| 项 | 改动前 | 改动后 |
|---|---|---|
| 丢 1 个分块的后果 | 整帧 2MB 作废，只能再要一整帧全量 | **只缺它带的那 2 条带**（画布 17 条带里 15 条仍有效） |
| 补画布的方式 | 一发 ~2MB 全量帧（拥塞时整发丢） | 渐进式轮转：**5 帧铺满**，单帧最大 **57KB**（全量帧的 12%），总流量 275KB < 460KB |
| 2K 全量端到端延迟 | 47.5 ms | **18.0 ms** |
| 1080p 全量延迟 | 32.2 ms | **14.0 ms** |
| 1080p 增量延迟 | 19.3 ms | **14.1 ms** |
| 自检 | — | capcheck 12/12 · codeccheck 15/15 · sigcheck 29/29 · **netcheck 19/19**（新增丢块章节）· uicheck 11/11 |

真机 e2e（2K、观众 1 人）：25.7 fps · 12 Mbps · **延迟 12~17ms** · 解码 3.8~4.2ms/批 · 画布完整=true · 坏块 0。

## 新线格式（GSJ2）

一个线路消息 = **一个分块**，自带 36 字节帧头 + 若干**完整**条带记录（条带绝不跨块拆分）：
magic/seq/ts/w/h/totalTiles/tileH/flags/**refresh**/**chunkIdx**/**chunkTotal**/**tilesMask**。

- `tilesMask`（整个逻辑帧的条带位图，每块都写同一份）→ 接收端据此**精确**知道该期待哪些条带、丢了哪几条。
- rtc 里的重组状态机（`asm`/`frameBuf`/1.5s 超时清理）**整段删除**：收到一块解一块，没有队列、没有僵尸槽。
- `Refresh` 是修复轮次号（0=稳态），观众端用它判断"修复在飞，别重复要"。

## 三个坑（都写进 PLAN.md R39~R43）

1. **逐块解码把帧内并行度丢光**：单块通常只带 1~2 条带，而 JPEG 解码是 CPU 大头
   （2K 一条带 ~3ms）→ 2K 全量解码 **7ms → 98ms**，延迟涨到 338ms。
   正解：`rtc.Config.OnFrames` 把邮箱里攒的块**成批**给出 + `Decoder.DecodeBatch` 一次并行解
   （批量上界 4 块：再大就变成"邮箱里压出延迟"）。
2. **"条带不跨块"⇒ 必须允许超大块**：我一开始把"装不下就降这条质量重编"的阈值定在 60KB，
   结果 2K 高细节画面被降质，**PSNR 掉 3.5dB**。实测（`out/msgsize`）pion↔pion 的
   DataChannel **512KB 消息照样送达** → 单条带超标称值就让它自己占一块更大的消息，
   阈值改成 1MB 的硬上限后画质与旧基线**完全一致**（34.97/33.54/33.71）。
3. **线格式变了必须做版本握手**：混版本不会报错，而是"接入成功但画面全黑"。
   已在 HTTP 接入双向互报 `proto`：同版本正常；老客户端 → **HTTP 409 +「双方版本不一致…」**
   （实测）；老分享端 → 新观众端在换 SDP 之前拦下。

## 观看端减负（第 3 件）

- `cmd/goshare/viewbuf.go`（新）：画面缓冲池 —— 复用固定两块内存，只把**变化过的条带行**
  从解码画布同步进去，交给界面时零拷贝；界面用完经 `ui.ShellConfig.Recycle` 还回来。
  取代了"每帧新分配 20MB + 整帧拷贝"（2K 下等于 600MB/s 垃圾）。
- `pixStat`（每帧扫 30 万像素）降到每 5 帧一次。
- 观看端新增两个指标：**端到端延迟**（帧 TS → 本地）与**解码跳块/坏块**，
  单列"本地产能不足"与"网络丢了"，别互相冒充。

## 遗留

- 多观众扇出（4 人以上）与无线丢包没压测；`spike/multiview` 可用，但结论建立在环回与有线。
- 分块级"精确补发（只重发缺的几条带）"还能再进一步（现在是一整轮轮转铺满）——
  需要观众端把 Missing 位图回报给分享端，属于下一轮。
- 线格式变更意味着**必须两端同时升级**（已由版本握手兜住，不会静默）。
