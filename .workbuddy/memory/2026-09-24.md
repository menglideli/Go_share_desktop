## 本次踩到的坑（都已写进 PLAN 风险登记 R18~R23）
1. **外部 SetWindowPos 移动 Gio 窗口 → 不再产生帧事件**（停在第 10 帧；不移动可跑 889 帧）。改用「采集副屏、观看窗留主屏」。
2. **RGB↔YUV 范围不匹配**：编码用 limited-range 而解码按 full-range → PSNR 23dB 且"提质量无改善"。统一 BT.601 full-range 后 34.8dB。
3. **解码画布并发访问**：解码器持久画布直接交给 Gio 渲染 → 撕裂/崩溃（退出码 0xCFFFFFFF）。改用画布池 + 渲染完归还。
4. **限帧判定卡边界**：严格 `< interval` 让 30fps 档只发 19.7fps。加 3ms 容差后 28.9fps。
5. **重组槽按数量清理误删活跃帧**：不可靠无序通道下分片乱序，活跃帧数超预期。只能按超时清理。
6. **别用随机噪声模拟桌面变化**：JPEG 对噪声 PSNR 崩到 20dB 以下，看着像编码坏了。
7. **采集耗时度量口径**：`WaitFrame` 含阻塞等待（DXGI 变化驱动），不能当 CPU 开销。拆分后：2K 等待 45.2ms / **处理仅 1.20ms**。
8. Gio 关窗后进程不退出 → 兜底 os.Exit(0)。

## 三个坑（R25 / R27 / R28）

**R25 首帧黑 —— 已修**
`capture.Source.Warmup()`：有限次数(3)+超时(600ms) 丢掉未初始化黑帧，**预热期不更新 `Last()`**。
实测 **10/10 → 0/10**，已固化进 `capcheck` 第 12 项。

**R27 观众退出致分享端静默卡死 —— 本次最贵的 bug**
- 症状：第一个观众退出后日志停在 `连接状态 closed`，**无 panic 无报错**，
  但此后所有接入都 `context deadline exceeded`；还残留幽灵观众（显示"当前 2 人"）。
- 根因（同一回调链上两处）：
  1. 在 pion 的 **ICE 状态回调里同步调 `peer.Close()`** —— 回调占着 ICE agent 的内部
     goroutine，Close 又要等 agent 收尾 → 互等死锁。
  2. 幂等用 `sync.Once`，而 `cleanup → Server.Drop → closeFn → cleanup` 是同 goroutine
     重入 → `once.Do` 永久阻塞。
- 修复：`go cleanup(...)` 挪出回调线程；幂等改 `mu + bool flag`。
- **反向变异**：改回同步 → 立刻复现卡死；改回异步 → 正常。唯一变量就是那一行 `go`。

**R28 持锁回调 / 回调环**
`Server.Kick` 持 `s.mu` 调 `closeFn`，而 closeFn 回头调 `srv.Detach` → 同锁自锁。
规则：**先摘记录、解锁、再回调**；`Drop`（移除+回调）与 `Detach`（只移除）语义必须分开。

# 阶段 5：健壮性（开篇）—— R32 观众接入缺全量帧

## 先还掉阶段 4 的欠账
桌面解锁后补做"画面内容级复验"：采集源（副屏同刻截图）非黑 98.2% / 亮度 208.1，
观看端收到并解码后 非黑 98.2% / 亮度 209.0 —— 对得上，链路内容正确。

## R32（本阶段最重要的发现）
**症状**：观看端收到的帧有 5/16 分带亮度为 0.0 —— 不是画面偏暗，是**条带从没被填过**。

**根因（三层，缺一层都不至于）**：
1. `sh.AddPeer()` 触发的 `ForceKeyFrame()` 只置标志，真正的全量帧要到下一帧编码（~33ms 后）
   才产生 —— 那一刻 DataChannel 往往还在 DTLS 握手，`SendFrame` 返回 `ErrNotOpen` **丢掉**；
2. `Encode` 末尾无条件 `havePrev = true` → 全量帧**只此一次**；
3. `CtlPLI` 定义了但正式链路**从没发送也从没处理** —— 观众丢了自己也不知道。
→ 增量帧只覆盖变化条带，静止区域**永远是黑的**。实测观众开局只有 **11.8%** 画面，
靠桌面偶然大幅变化才在 **12 秒 / 226 帧**后补全。这就是用户报的"全黑看不见东西"。

**修复（三条互相独立的恢复路径）**：
① 通道就绪后补一次请求（`WaitReady` → `RequestKeyFrame`）；
② 接入窗口内密集补（`KeyBurst` 3s / 每 400ms 一帧全量）；
③ 观众端不完整或丢片 → 发 `CtlPLI` → 分享端补全量。
**刻意不做**常态周期全量（实测 3s 周期让带宽 5.5 → 9.2 Mbps，+67%），稳态交给 ③。

**反向变异矩阵**（统一前提：注释掉 AddPeer 的 ForceKeyFrame）：
| 生效路径 | 首帧 | 补全 |
|---|---|---|
| 无 | 11.8% | 226 帧 / 12 秒（偶然） |
| ①② | 17/17 · 97.8% | 首帧即完整 |
| 仅① | 17/17 · 98.2% | 首帧即完整 |
| 仅③ | 11.8% → 17/17 | **1 帧 / ~33ms** |
②未单独隔离验证（③在客户端无法独立关闭）——不宣称它被单独证明过。

**稳态回归**：首帧 17/17 非黑 98.2%；全量帧计数 6→11 后停止增长；带宽 0.0~2.3 Mbps；编码均值 4.9~7.1 ms。

- 踢人影响面：中途踢 1 人，其余 4 人 12 秒内各多收 **357 帧，分毫不差** → 无影响面
- 上限：`-max 2` + 4 人抢 → 2 进 2 拒，拒绝干净
- 名额回收（幽灵观众回归）：正常 Bye 立刻 / 关 Peer 同秒 / **taskkill 强杀 → disconnected →
  5s 后释放**；三种释放后重试补位均成功

### ⚠️ 本轮最大的坑：控制台窗口自摄入（差点让整批数据失效）
从终端启动的 Go 控制台程序会自己弹窗，**这个窗口进了采集画面**。观看端每打印一行就滚屏
→ 画面剧变 → 触发全量帧 → 又打印一行，**自激振荡**。
污染读数 84→108 Mbps / 全量帧 186；干净基线其实只有 0.0~4.2 Mbps / 全量帧 1。**差 10 倍**。
危险在于它很有说服力（fps/帧数都正常），很容易误判成"编码器档位太高"去改本来正确的代码。
修法：分享端 `-display 1` 采副屏，控制台窗口留在主屏。
**判据：只要"观众 0 人"时带宽不接近 0，先怀疑自摄入。**

### 其他三个验证方法坑
- 公平性统计把中途被踢的算进极差 → 假 50%（实际在线的极差 0.1%）
- 重试成功者用"首次尝试时刻"当 fps 分母 → 29.6 fps 显示成 3.6 fps
- `tasklist`/`taskkill` 在 Git Bash 里不加 `MSYS_NO_PATHCONV=1` 会**静默失败**（一整组实验白跑）

### 顺带发现的两个可优化项（不是 bug，已进 PLAN 待办）
