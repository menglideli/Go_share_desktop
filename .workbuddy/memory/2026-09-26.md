## 用户实测反馈修复（下午）：颜色塌陷 + 扇出重构

**① 观看端红→绿**：根因是 convert.go 色度公式未钳位 —— 纯红 Cr 算出 256，
uint8 回绕成 0，解码端按 -128 反变换 → 红塌成 (0,183,0) 暗绿（纯蓝 Cb 同理）。
修复 clamp8。codeccheck 新增第 6 项「8 色饱和色卡逐通道断言」（反向变异验证过：
撤钳位 → FAIL）。真实链路复核（e2e62，multiview dump vs 1.5s 内截图）：
逐通道 MAE 修复前 R=25/G=17/B=3（通道选择性）→ 修复后 1.7/1.1/2.0（对称 JPEG 噪声）。

**踩坑**：修复后连跑 6 轮 e2e 假 FAIL —— `go build redwin && go build goshare`
的 && 链在 redwin 编译失败时中断，goshare 没重建，全是旧二进制（约束 53 第二次踩）。
定位过程还排除两个方法论污染：观众窗"无限镜子区"（占屏 52% 不可比）、
dump 与截图间隔几十秒的漂移。干净判据 = 无窗口 multiview + 即时截图
+ 逐通道 MAE + 差异空间分布（全屏散布=缺陷，局部集中=漂移）。

**② 第三台卡顿 → 扇出重构（用户提议的"写缓存/读缓存"架构）**：
旧实现 emit 在采集 goroutine 上给每观众串行 SendFrame，而 SendFrame 内部
每次都 Marshal（2K 全量≈2MB 拷贝 ×N 人）。基线 4 观众：观众仅 13.9~15.3fps、
极差 19.5%。重构：encode+marshal 一次进 latest 共享缓存（atomic.Pointer），
每观众独立 sendLoop 读最新帧 SendWire 分片发（latest-wins 慢者跳帧）。
改后 **21.2~23.8fps（+55%）、极差 1.3%**。剩余上限是单路 SCTP 吞吐，非 host CPU。
